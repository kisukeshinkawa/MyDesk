### 1-2. 点数決定の5層構造（今回の混乱の根源）

```
最終点数 = 質判定層( min( L層, gap12層 ) を上書き )
  1層: race_predictor.py 132-148   gap12ハードコード(4〜10点) ← A2の主役・温存
  2層: lgbm_predictor.py 954/1114  L層 _load_learned_points   ← A2化済(=40で無効化)
  3層: lgbm_predictor.py 1316      bets_wide[:18] → bets_full  ← 参考表示用・未対処
  4層: race_predictor.py 172-180   軸絞り                      ← A2化済(撤去)
  5層: lgbm_predictor.py 1120-1170 質判定層(p1_top/gapで18/12点等を最終決定) ← 未対処・これが支配
```

- dry-runでは bets=6点(A2が効いて見える)が、実投稿は18点(質判定層が上書き)。
- 前任はこの食い違いに4日間気づかなかった（dry-run確認のみで「完了」と誤報告）。

### 1-3. 資料間の数字の食い違い（要注意）

回収率の「ベースライン」が資料によって異なる:

| 出典 | 時期・サンプル | 回収率 |
|---|---|---|
| 検証v4素材(指示T) | 6/28・3044件 | R方式 85.9%（L方式 50.4%） |
| 指示V'ガイド | 6/29-30・3236件 | A1/B/A2一致 90.8%（38.8%・7.0点） |
| HANDOFF | 7/6・3968件 | 4方式ほぼ同じ 約94.6% |

期間・件数が違うので矛盾とは限らないが、**約1ヶ月で基準値が85.9→94.6%と9pt動いている**。
これは日次分散が大きい証拠であり、「CI下限>100%で判定・分散併記」の規律が正しいことの傍証でもある。
→ 改善案4で「統一評価窓の事前登録」を先にやる理由。

### 1-4. 確定済みの知見（揺るがない前提）

- 点数決定の複雑な加工（軸絞り・L層学習点数・毎晩の点数最適化）は無意味。効くのは「7点前後に絞ること」だけ。
- L方式(学習層)は回収率を半減させていた（50.4% vs 85.9%、CI下限+30.56で確実）。点数最適化4本の隔離は正当。
- 旧background_learn（無検証・即上書きの毎晩再学習）は害。復活させるなら指示W PART3の「ゲート通過のみ反映」設計で。
- どの方式でも回収率は100%未満。絶対的黒字は未達成で、指示ACは「相対改善(94.6→96-97%)」を提案（ただし未実測）。

## 2. 構造的な問題点（重要度順）

### 問題1: 点数決定の分散（アーキテクチャ負債）★最重要
5層に分散した点数決定が、A2改修を2回「効かせない」事故を起こした
（1回目: pycキャッシュ、2回目: 質判定層の上書き）。
層を1つ潰すたびに次の層が現れる構造で、**部分パッチでは再発する**。

### 問題2: 「コードの状態」と「実際に動いているもの」の乖離を検出する仕組みがない
- dry-run成功≠本番反映（経路が違う・pycが残る・常駐プロセスが旧コードを保持）。
- 実投稿の点数を機械的に監視する仕組みがなく、18点のまま4日間気づかなかった。
- daemンがどのバージョンのコードを読んでいるか、ログから判別できない。

### 問題3: 方針の根拠となる数字が未実測
指示AC（相対改善路線）の SS75.8%/C95.6%/EV89.9% は全て見込み値。
これを実測しないまま A2完遂に労力を注ぐと、調査結果次第で同じ箇所をもう一度改修することになる。

### 問題4: データ基盤の劣化
- actual_course全件空・entry_changed全件0 → 指示W(組み合わせ特徴)が着手不能。
- race_entries 5/7以降未取得の疑い → 放置すると直近データでの検証自体が信頼できなくなる。
  8/2現在も続いていれば約3ヶ月分の欠損であり、宿題Bの直近サンプルにも影響し得る。

### 問題5: 監視の空白
蘇生3経路封鎖の副作用として、死活監視も止まっている（check_daemon_alive cronごと停止）。
daemンがハングしても誰も気づかない状態が1ヶ月続いている可能性。

## 3. 改善案

### 改善案1【方針】宿題Bを先行し、A2は「点数エンジン一元化」として1回で本番改修する

推奨順序: **B(調査・読み取り専用) → 方針決定 → 本番改修は1回だけ**。

理由:
1. A2完遂は成績を変えない改修（4方式同等が確定済み）。急ぐ利益がない。
2. 現状は「旧点数18点で安定稼働・ベースライン凍結」= pre-A2と同じ挙動で危険がない。
3. 調査Bの結論次第で点数戦略ごと変わり得る（グレード除外・レース選別層の追加等）。
   先にA2を完遂すると、質判定層周辺を二度改修することになる。本番改修は不可逆なので回数を最小化する。
4. 調査Bは読み取り専用・本番非干渉で、失敗してもやり直せる。

### 改善案2【アーキテクチャ】点数決定を単一モジュールに集約する

質判定層だけを潰す部分パッチではなく、点数決定を1ファイルに一元化する:

```
predictor/bet_count_policy.py（新規・唯一の点数決定箇所）
  decide_bet_count(gap12, gap23, p1_top, grade, weather, race_no) -> (n_bets, reason)
```

- 5層すべてがこの関数に委譲。中身は当面A2（gap12点数＋6号艇頭除外）。
- 決定のたびに1行ログ: `点数決定: N点 (policy=A2, gap12=xx, reason=...)`
- 質判定層は「点数決定」から外し、投稿可否・conf表示のみに役割を縮小
  （グレード分類器温存＝罠3と同じ思想。判定ロジック自体は捨てない）。
- 効果: 「6つ目の層」の存在可能性を構造的に排除。将来、調査Bの結論で戦略を変えるときも1ファイルの変更で済む。

### 改善案3【再発防止】「実際に動いているもの」を機械的に検証できるようにする

1. **BUILD識別子**: `PREDICTOR_BUILD = "2026-08-XX-a2-vN"` を定義し、daemン起動時と各予想ログに出力。
   ログを見れば「daemンがどのコードを読んでいるか」が即判別でき、pyc/旧プロセス問題を一目で検出できる。
   （MyDeskのMYDESK_BUILDと同じ流儀）
2. **投稿点数のセルフチェック**: 投稿直前に絞り点数を期待レンジ(例: 3〜10点)と突合し、
   範囲外ならWARNログ＋投稿本文に出さない等の安全弁。「18点のまま4日」の再発を機械的に防ぐ。
3. **pycの恒久対策**: systemd unitに `Environment=PYTHONDONTWRITEBYTECODE=1` を追加し、
   `ExecStartPre` で__pycache__削除。手順書の「pyc消し忘れ」を人間の注意力から仕組みに移す。

### 改善案4【調査B】実測計画（事前登録つき）

Step 0: **評価窓の事前登録**（着手前に固定・後から動かさない）
  - 期間（例: 6/6〜直近）、最低N（200 or 500）、判定閾値（CI下限>100% / 相対比較はCI非重複）、
    クラスタブートストラップ2000回、日次分散併記。
  - §1-3の「基準値9ptブレ」を断つため、以後すべての数字を同一窓で比較する。
Step 1: `ev_backtest.py` 実行（既存・21時以降・setsid nice -19）→ 会場群×decileのCI確認。
Step 2: `verify_grade_roi.py` 新規作成（verify_4m拡張・グレード別）
  - まず数百件で集計ロジック検証 → フル実行。
  - 判定: SS級CI上限 < 全体、C級が高ければ指示ACの主張を支持。
Step 3: 買い方軸（本命/穴目/極限絞り）を同じ枠組みで追加。
Step 4: 結果を1枚に統合 → 新川さんが方針決定（相対改善 vs 的中率ブランド）。

前提の健全性チェック（Step 0と同時）:
  - race_entries の5/7以降欠損を確認。欠損が直近サンプルを汚していれば評価窓の設計に反映。

### 改善案5【データ基盤】指示Z（actual_course）を早期に仕込む

- `full_scraper.py` fetch_result(546行付近)は既にスタート情報をfetch済みで、パース追加だけで遡及取得可能。
- 読み取り系の改修でリスクが低く、貯まるまでに時間がかかるデータなので、**調査Bと並行して早めに仕込む価値が高い**。
- これが埋まると指示W PART1（外張り痕跡・隊形カテゴリ）が解禁される。

### 改善案6【運用】監視を「検知のみ」の形で復活させる

- check_daemon_alive.sh を「再起動はしない・通知のみ」に改修して戻す
  （V'ガイドの推奨と同じ。蘇生スクリプトではなく純粋な死活監視に）。
- 本番改修の再開時セット: background_learn無効確認 → start → 翌朝に
  ①投稿あり ②絞りN点が期待値 ③models/点数タイムスタンプ6/28のまま ④daemン生存、の4点確認。

## 4. 推奨ロードマップ

```
Phase 0: 現状実測（EC2アクセス確保後・30分・読み取りのみ）
  - daemン状態 / daemon.logの「絞りN点」直近値 / ベースラインタイムスタンプ
  - race_entries・actual_courseの欠損状況 / 7/6以降に何か変わっていないか
  ※7/6→8/2の空白があるため、本書の前提が生きているかをまず確認

Phase 1: 調査B実測（数晩・21時以降・読み取り専用）        ← 改善案4
  並行: actual_courseパース実装（本番非干渉）              ← 改善案5

Phase 2: 方針決定（新川さん）
  - 実測数字で指示ACを支持/棄却 → 点数戦略の最終形を決める

Phase 3: 本番改修（1回だけ・頭を冷やして）
  - 点数エンジン一元化（Phase 2の結論を実装）              ← 改善案2
  - BUILD識別子・セルフチェック・pyc対策を同時に入れる      ← 改善案3
  - bak取得 → 改修 → pyc全削除 → 再起動 → 実投稿値で確認するまで完了としない

Phase 4: 運用正常化
  - 検知のみ監視の復活 / 翌朝4点確認 / 報告書v4確定         ← 改善案6
```

## 5. 判断をお願いしたいこと

1. **順序の承認**: 「調査B先行 → 本番改修は1回」の方針でよいか（改善案1）。
   A2を先に完遂したい場合はその判断も可能だが、質判定層の改修を二度やるリスクを許容することになる。
2. **改修の粒度**: 本番改修時に「質判定層のみ修正（最小）」か「点数エンジン一元化（改善案2・推奨）」か。
3. **実行環境**: EC2上でClaude Code CLIを動かす件（前回提案）。Phase 0以降はEC2アクセスが必須。
